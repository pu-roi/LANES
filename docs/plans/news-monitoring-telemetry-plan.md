## Evidence and implemented scope

Before this change, `NewsFeedCheckpoint` retained only the latest check/success/error, `NewsArticle` retained current retrieval evidence, and immutable versions/runs retained extraction history. Discovery summaries and fallback outcomes were transient. The approved telemetry now records both workflows without changing flood evidence or lifecycle state. No durable per-claim publication timestamp is available for collection-to-alert measurement.

GET `/api/v1/admin/news/monitoring` is staff-protected and read-only. Its CRUD layer aggregates body counts and newest extraction status per article in SQL, without transferring article bodies or result JSON. It returns at most ten current missing/error articles, ordered by last sighting and ID. A stored retrieval error takes precedence over a retained older body; a newer failed extraction takes precedence over an older success. Unknown publishers retain their source identifier. Empty storage returns zero counts. Storage failures return a sanitized 503.

Sources & feeds adds Pipeline using the existing responsive drawer. One column at narrow widths, three body metrics at 360px and above, and two extraction columns at desktop widths; shared tabs/dialog retain keyboard and safe-area behavior. Refresh is GET-only. Error/retry and empty states are explicit. Current totals remain distinct from discovery-run counts. `NewsTelemetryHistory` presents independently paginated discovery/fallback sections with feed outcomes, counters, retrieval status, assessment and saved retry delay. Alert delay remains unavailable.

## Approved storage — implemented

The developer approved this proposal with “go proceed” on October 3. Revision `c5a7e9d2104f` adds the four tables below, without backfill or changes to existing evidence/lifecycle fields. All timestamps are timezone-aware UTC. Each attempt has a unique UUID correlation token and conditional finalization keyed to its row identity. Start-time and child foreign-key indexes support history reads. Staff discovery and fallback require a user actor; collector discovery has a null actor. Telemetry omits secrets, response headers, article bodies and arbitrary exception strings.

1. **`news_discovery_runs`**: integer primary key; unique UUID `correlation_id`; nullable `actor_id`; `trigger` constrained to staff/collector; `status` constrained to running/completed/failed/interrupted; required `started_at`; nullable `finished_at`; nullable bounded `error_code`. Finished statuses require a finish time. Record the start before collection; finalize even on normal partial feed failure. An abandoned running record is explicitly interrupted after a documented timeout, never assumed successful.
2. **`news_discovery_feed_runs`**: integer primary key; required `discovery_run_id` foreign key; required publisher `source_id` and `feed_url` snapshot; required probe `status`, `checked_at`; nullable bounded `error_code`; required nonnegative `entries_seen`, `candidates_saved`, `body_errors`, `scope_unresolved`, all default zero. Unique `(discovery_run_id, source_id, feed_url)`. Counts refer to that feed attempt, not distinct articles across feeds. Feed status and candidate counters are independent. Source identifiers refer to external configuration, so they are provenance snapshots rather than a duplicated publisher registry.
3. **`news_fallback_lookups`**: integer primary key; unique UUID `correlation_id`; required original `article_id` foreign key with RESTRICT deletion; required `actor_id` user foreign key; required original `content_fingerprint` snapshot; required `retrieve_articles` boolean; constrained `status` running/completed/failed/interrupted; required `started_at`; nullable `finished_at`, bounded `error_code`, and nonnegative `retry_after_seconds`. Search success with zero matches is distinct from provider failure/throttle. A repeated HTTP lookup creates a new attempt; finalization of that attempt remains idempotent.
4. **`news_fallback_lookup_leads`**: integer primary key; required `lookup_id` foreign key; required nonnegative response `ordinal`, unique per lookup; required `article_url`; nullable publisher `source_id`; nullable `retrieved_at`; required retrieval status constrained to not_requested/retrieved/failed; nullable bounded `error_code`; nullable same-event assessment label. Store provider result identity and assessment, never treat an alternate lead as independent flood confirmation. Do not copy alternate article text into telemetry.

Migration: create only these tables, constraints and indexes; downgrade removes children before parents. Existing data and extraction JSON remain unchanged. Test Alembic upgrade/downgrade on a disposable PostgreSQL database before rollout. Instrument both staff POST discovery and the existing collector through their shared service, so CLI activity is included. Keep telemetry failures visible and avoid falsely reporting collection success; define partial commits explicitly because current discovery commits per feed. Fallback GET currently performs external work: persist its telemetry without activating reports or changing evidence, and document that inspection now records an attempt.

Implemented reads: staff GET `/api/v1/admin/news/monitoring/discovery` and `/monitoring/fallback`, with stable start-time/ID ordering, total counts, five attempts per page by default and a maximum page size of twenty. Child rows are loaded only for that page. Empty history means no recorded attempts, not a healthy pipeline. No historical backfill and no mutation/network work on history reads.

## Persistence, recovery and rollout

`discover_news` records a start before collection for both staff and the collector. Each existing per-feed commit now includes feed telemetry, so an error later in the run preserves earlier committed outcomes. Candidates saved counts distinct URLs written during that feed attempt, including refreshed existing candidates; it is not a new-article count. Body errors include attempted retrievals that did not become candidates. Partial feed failures finalize the parent as failed with a sanitized code; unexpected failures rollback the current feed and finalize the parent as failed.

Fallback input is captured before the start-record commit, preventing ORM expiration/concurrent article revisions from changing lookup inputs while retaining the old fingerprint. Lead metadata and finalization commit together. Repeated finalization cannot duplicate children or overwrite a completed/failed/interrupted attempt. A telemetry storage failure returns a sanitized 503 or causes the collector to fail visibly. If storage cannot finalize, the durable start remains unresolved.

New work marks running attempts older than two hours interrupted. This exceeds the bounded normal collection/search budgets. History GETs never perform recovery writes; until new work arrives, an unfinished attempt remains running with an unresolved outcome. Finished timestamps and actor/trigger constraints are enforced by the database.

The migration passed full fresh PostgreSQL upgrade, downgrade to `f29b6c8d104e`, re-upgrade and repeated upgrade. Prior article evidence survived; model column/nullability/check/index sets were verified. Both disposable databases were removed. Local LANES successfully ran `alembic upgrade head` and now reports `c5a7e9d2104f`. History reads return zero records without writes. Production rollout is pending: run the migration before deploying the updated API/collector. New clones use the standard `cd backend` then `alembic upgrade head`; no new dependency is required.

## Collection-to-alert delay and later gate

Defer this metric to the review/publication backend checkpoint. It requires a durable published claim revision linked to immutable input and its original collection timestamp. First sighting, publication date, extraction completion and feed success are different clocks. Do not use extraction latency as alert delay. The alert/decision schema is outside this monitoring proposal and requires its own agreement and approval.
